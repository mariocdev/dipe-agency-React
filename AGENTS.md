# Dipe Agency: instrucciones de trabajo

Lee `PLAN_PARA_TERRA.md` para el estado y siguiente tarea. Consulta `git status --short` una vez antes de editar para preservar el trabajo en curso, sin volcar diffs extensos. El usuario publica por FTP y revisa **todos los cambios en el servidor**; entrega los archivos necesarios y espera sus observaciones.

- WordPress conserva URL, menús, logos, entradas y CPT. `dipe-core` define CPT/ACF/REST; el tema proporciona el shell, configuración pública y metadatos. Home y demás páginas corporativas tienen estructura, texto e imágenes fijas en React/código. Los enlaces de menús y logos sí son editables en WordPress.
- Rutas editoriales acordadas: entradas nativas en `/blog/{slug}/`, categorías nativas en `/categoria/{slug}/`, archivo del blog en `/blog/`; proyectos permanecen en `/proyectos/`. WordPress debe resolver la URL y su estado HTTP antes de que React pinte la vista.
- Crea un componente por sección o plantilla con responsabilidad clara. Mantén `App.jsx` como composición y resolución de rutas; lleva el contenido fijo de Home a `Home.jsx` o un módulo cercano cuando amplíes esa página. Comparte lógica de dominio (`api.js`, normalizadores, enlaces), no fuerces un componente visual genérico para tarjetas con diseños distintos.
- Usa `tokens.css` y `fonts.css` para identidad visual. Un valor solo necesita token global si es de marca o se repite; el ajuste exclusivo de una sección queda en su CSS. Divide gradualmente `styles.css` por componentes al tocar esas secciones, preservando orden de cascada y responsive. Evita otro bloque grande de CSS global.
- No escribas el dominio temporal `bonsolis.servidordepruebas.net` en nuevos componentes ni en CSS. Para medios fijos, centraliza rutas y resuélvelas desde la URL del sitio o importa assets locales; la sustitución del dominio debe requerir un solo cambio. El contenido editorial procede de REST, no de URLs copiadas a mano.
- Para imágenes ACF por REST, `acf_format=standard` proporciona el objeto completo; el formato ligero puede ser solo ID. Reutiliza `projectHomeCardImage`; usa las respuestas reales que facilite el usuario tras su revisión en el servidor antes de añadir otra transformación. Evita inyectar HTML en títulos si basta texto.
- La sección de reseñas usa dos opiniones reales facilitadas por el usuario y las repite para tener cuatro tarjetas. Identifica las repeticiones; no las cuentes como opiniones adicionales ni inventes testimonios. La valoración agregada solo representa la fuente auténtica. Sigue `docs/resenas-home.md`.
- Formularios: sigue `docs/formularios.md`. Prioridad del usuario: sencillez y rendimiento; evitar por defecto Elementor y plugins nuevos de formularios o SMTP. React dibuja los formularios; `dipe-core` validará y guardará entradas privadas diferenciadas. La bandeja **Solicitudes** de `wp-admin` ya está preparada con filtros, búsqueda y detalle de solo lectura, pero aún no hay endpoint ni formulario conectado. El correo usa `wp_mail()` con el SMTP del hosting configurado en PHPMailer; los dos buzones y contraseñas se gestionan desde **Ajustes > Correo Dipe** en WordPress, nunca en Git. CookieYes será el único gestor de cookies. No supongas campos ni destinatarios definitivos; para CV, restringe descargas y define conservación antes de activarlo.
- **Flujo de revisión decidido por el usuario:** no ejecutes comprobaciones locales por iniciativa propia: ni servidor de desarrollo, navegador, capturas, tests, lint, `git diff --check`, llamadas de prueba a la API ni rondas visuales de escritorio/móvil. Las indicaciones de prueba en documentos anteriores quedan supeditadas a esta regla. Si cambia React/CSS, ejecuta `pnpm build` **una sola vez al finalizar**, únicamente para generar los assets que el usuario debe subir por FTP; no lo conviertas en una campaña de pruebas. Si cambia solo documentación o PHP, no compiles el front. Informa de un fallo de compilación si impide entregar assets.
- Entrega iteraciones pequeñas con lista breve de archivos modificados y qué subir por FTP. No afirmes que una vista funciona hasta que el usuario la revise en el servidor; espera sus capturas o comentarios para ajustar el código. No crees abstracciones o pruebas que solo dupliquen el código existente.

## Continuidad entre entornos y cierre de tareas

- **GitHub es la fuente de verdad del código y la documentación versionada.** Codex Desktop modifica los archivos locales; Codex Cloud trabaja desde GitHub en ramas independientes y mediante pull requests. Antes de continuar en otra sesión, consultar `CONTEXTO-PROYECTO.md`, el estado Git y la rama correspondiente.
- Al terminar una tarea relevante, actualizar `CONTEXTO-PROYECTO.md` con hechos verificados, decisiones y pendientes. Los cambios de documentación que describan una implementación se incluyen con su código en el mismo commit cuando correspondan.
- No sobrescribir cambios ajenos ni usar operaciones Git destructivas. No hacer merge ni push directo a `main` sin autorización expresa. Cuando sea seguro y esté autorizado, preparar commit y push en una rama de trabajo; indicar cualquier pull request o cambio aún pendiente de integrar y si el entorno local necesita `git pull`.
- El cierre de cada tarea de programación debe: actualizar el código aplicable; actualizar el contexto cuando haya avances importantes; ejecutar una sola vez `pnpm build` al final solo si cambió React o CSS; preparar commit y push en la rama de trabajo si están autorizados; enumerar con precisión los archivos que el usuario debe publicar por FTP; y proponer el siguiente paso. Un cambio solo documental o PHP no requiere compilación del front.
- Git no despliega: no realizar publicaciones FTP automáticas ni modificar producción sin autorización expresa del usuario. La versión realmente publicada y su validación solo se anotan tras confirmación del usuario.
